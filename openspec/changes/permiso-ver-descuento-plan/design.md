# Design: Permiso de rol para ver el campo Descuento

## Technical Approach

Clone the `puede_editar_descuento_plan` plumbing (change `mrc-plan-descuento-fijo`, migration 048) for a new boolean `roles.puede_ver_descuento_plan`, flipping only the default (`TRUE` instead of `FALSE`). No new architecture, no new layer, no new endpoint: the existing role-permission pipeline already carries booleans from `roles` → repository → `req.usuario` / `login()` payload → `localStorage` → frontend. The only new behavior is one derived flag in `frontend/cotizar/cotizar.js#renderAjusteField` that short-circuits rendering. Verified against current code, not assumed (see File Changes for exact anchors).

## Data Flow

    roles.puede_ver_descuento_plan
      → roles.repository CAMPOS  → admin panel (checkbox + badge)
      → usuarios.repository CAMPOS_ROL → aplanar()
          → middleware/auth.js req.usuario   (backend: unused — cosmetic only)
          → auth.service.js login() payload → localStorage → auth.getUsuario()
              → cotizar.js renderAjusteField → render '' | disabled | editable

`resolverDescuentos()` is deliberately absent from this graph.

## Testing Strategy

| Layer          | What                                                                                                                                     | How                                                                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Unit (backend) | No new logic to test — the flag is inert server-side                                                                                     | Run `npm test --prefix backend`; the existing `resolverDescuentos` suite is the regression guard proving the value is unaffected |
| Manual/live    | Admin unchecks the permission for a role; user re-logs in; MRC/SEGUCOOP shows no Descuento field, Recargo intact, Carta Oferta still 10% | Playwright with `test@test.com` (rol agente) after re-login                                                                      |
| Regression     | Role with `puede_editar=true` and role with default `ver=true` unchanged                                                                 | Same live pass                                                                                                                   |

No frontend unit-test harness exists in this repo — matching the precedent, no frontend tests are added.

## Threat Matrix

N/A — no routing, shell, subprocess, VCS/PR automation, executable-file classification, or process-integration boundary. Note the permission is cosmetic and MUST NOT be documented or reviewed as an access control.

## Migration / Rollout

Single additive migration, applied against real Supabase **only with Kevin's explicit confirmation** (project convention). Order: migration first (default TRUE keeps prod identical), then code. Rollback: N1 `UPDATE roles SET puede_ver_descuento_plan = TRUE`; N2 revert the commit (column inert); N3 `DROP COLUMN`. Cached `auth.getUsuario()` means a permission change needs a re-login to take effect — must appear in the verification steps.
